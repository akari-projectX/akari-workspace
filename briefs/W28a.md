# W28-a — servers, landing nodes, entrances, per-entrance accounting (panel + agent, T1, proto change)
Panel migrations 1030–1044 (W28-b gets 1045–1052, W28-c 1053–1059). Proto fields 30–35 (W28-b may use 36–39).
Implement PLAN D2, D3 and §5 (relay = entrances of a landing node) per research/db-schema-review.md and SPRINT R43 + Q1:
1. **Servers (Q1)**: new `servers` table, one machine = one agent identity; move machine-level columns off `nodes` (enrolment/CSR identity, agent version, machine metrics, rollout targeting, nftables, etc. — follow the review's list). A node = one inbound protocol config on a server (D2: one node, one protocol). Admin API groups nodes by server. Delete multi-inbound editing code paths.
2. **D3**: drop `node_users.manual` and all manual-assignment logic/endpoints; access is derived only from plans → node groups → entrances.
3. **Entrances**: every landing node has a built-in "direct" entrance (can be disabled) plus N external relay entrances (name, connect host:port, multiplier (base; D9 rules come in W28-b — leave a clean extension point), allowed node groups, relay egress IPs). Tables per the review (`entrances`, `entrance_group_members`, `entrance_users`, `entrance_users_departed`) replacing node_users / node_users_departed / node_group_members. Subscription lists each usable entrance as its own node ("香港 直连", "香港 IPLC 2.0x").
4. **Derived inbounds (D2 technical)**: each relay entrance auto-derives an inbound on the landing node's xray: same protocol/params as the main inbound, different port, independent per-user credentials, system-managed (not shown in admin). Panel computes the per-inbound user list; agent applies it blindly (agent knows nothing about groups).
5. **Source-IP allowlist**: agent applies nftables rules so a derived inbound only accepts connections from that entrance's relay egress IPs (kernel filtering, checked on new connections only). Idempotent, own table/chain, cleaned on removal; document required capabilities; degrade with a clear warning if nftables is unavailable (credential isolation is the primary control).
6. **Per-entrance accounting (R43)**: xray stat key = user UUID + entrance id (use the review's short per-node `wire_no` to keep keys short); traffic tables gain entrance_id per the review (incl. `traffic_entrance_daily` replacing `traffic_node_daily`; partition `traffic_daily` by month as the review recommends); SQL flush bills each entrance with its multiplier. Tests MUST prove: the same user's traffic on two inbounds is settled separately; removing the user from one inbound doesn't affect the other.
7. **Revocation**: downgrade/expiry/ban removes the user only from the affected inbounds and kills their live connections on those inbounds immediately.
8. **Entrance health**: panel periodically TCP-probes each external entrance; on failure hide it from subscriptions and raise an alert (existing alert channels); auto-restore on recovery.
9. **Q3**: daily traffic and plan monthly reset use the site timezone (`panel_settings.timezone`, default Asia/Shanghai) — implement here since these tables change anyway.
10. Agent: benchmarks before/after (§ Agent performance) incl. the cost of one extra derived inbound and nftables.
11. Smoke: extend smoke.sh to cover a relay entrance end to end (derived inbound up, per-entrance traffic billed, removal isolation).
Merge order: panel PR(s) first, then agent PR. Keep W28-b/W28-c (parallel workers) in mind: they build on the entrance/user tables — land the schema PR early and small if you can, and say in your report when it's merged-ready.
