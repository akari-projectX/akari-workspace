# Akari 代码质量与安全审查（2026-10-02）

范围：`akari-panel`（Rust，main @ e4ba08d）与 `akari-agent`（Go，main @ d6fbff7）的核心链路：mTLS/注册/续期、OpenChannel 会话与收敛状态机、流量上报与结算、xray 门控与限速、心跳/指标、自更新。
方法：通读上述路径源码；在本机运行 agent 基准（`go test -bench`，4 vCPU Xeon 容器）与 `go test -race` 验证所提出的 Go 重构；面板侧未构建（估算项已注明）。
标注：**[已测]** = 本机实测；**[读码]** = 由代码路径推导。

先说结论：这套代码的安全设计是成熟的（mTLS + 证书序列号身份 + 吊销墓碑、一次性 token 只存哈希、CSR 强校验、无命令注入、无 `unwrap` 崩溃点、流量上报有多层上限与背压）。真正的问题集中在四处：**面板把 argon2 放在 Tokio worker 上同步跑**、**agent 在持有 `applyMu` 时做可能永久阻塞的发送**、**双方都没配 gRPC 消息上限（≈1.8–3 万用户/节点的静默悬崖）**、**gRPC TLS 握手无并发上限**。性能上最大的浪费是 agent 每 10 s 全量重发 1 万行未变化的计数并在核心锁内做 3 万次分配。

## 一、[严重漏洞/缺陷]（Critical）

### C1. 面板：argon2 在异步 worker 线程上同步执行，登录/注册洪水可拖垮同进程的 Agent gRPC 流 [读码]

- `akari-panel/src/auth.rs:230-249` `hash_password` / `verify_password` / `scrub_password` 直接调用 `Argon2::default()`（OWASP 默认参数 m=19 MiB, t=2：单核约 40–80 ms）。
- 调用点全部在 `async fn` 内同步调用：`api.rs:242,248`（login，含对未知账号的 `scrub_password` 等时补偿）、`signup/register.rs:357`、`signup/reset.rs:238`、`signup/profile.rs:91`、`api.rs:990`。全仓没有一处 `spawn_blocking`。
- web、gRPC、flush、LISTEN 共用同一个 `#[tokio::main]` 多线程运行时。每次登录占住一个 worker 50–80 ms。限流 `login_limit.rs` 只对**失败**计数、按 IPv4 地址 / IPv6 **/64** 分桶（PER_IP=20/15 min）：一个 /48 的攻击者有 65k 个桶 → 理论 1400 req/s → 需要约 90 个 worker-秒/秒，而机器只有 16–20 个 worker。
- 后果链：runtime 饱和 → tonic/h2 无法及时应答 agent 的 keepalive PING（agent 侧 `Time 30s + Timeout 10s`）→ **全部节点同时掉线** → 重连风暴（见 W6 无抖动）→ 面板更忙。这把"登录接口 CPU 消耗"放大成了"控制面整体不可用"。
- 修复：`tokio::task::spawn_blocking` **加** 并发信号量（否则 blocking 池最多 512 线程 × 19 MiB = 9.7 GB 内存反而成了新攻击面）。见第三节 B。

### C2. Agent：持有 `applyMu` 期间调用可无限阻塞的 `send` —— 面板"活着但不读"时，fail-closed 租约失效、SIGTERM 无法优雅退出 [读码]

- `akari-agent/agent.go:464-472`：`send` 在 `sendCh`（容量 256，`:430`）满时只等 `ctx.Done()`；writer goroutine 在 `stream.Send` 上受 HTTP/2 流控阻塞时，256 条后 `send` 永久阻塞。
- 阻塞点都在 `applyMu` 之下：`handleDown`（`:634-635`）→ `applySnapshotLocked` 的 `a.finals.flush` + `send(a.helloLocked())`（`:702-704`）、`applyDeltaLocked`（`:757`）、`finalQueue.flush` 还同时持有 `q.mu`（`:952`）。
- 触发条件：对端 TCP 与 h2 PING 正常（keepalive 探测不到）但应用层停止读流——正是 C1 的面板饱和、或面板 `store_heartbeat` 串行等慢 Valkey 的场景。
- 后果：`checkLease`（`:816-820`）要先拿 `applyMu` 才能拆 xray → **租约到期也拆不掉，节点在失联状态下继续服务（脱管）**；`gracefulStop`（`:333`）同样拿不到锁 → SIGTERM 挂到 systemd `TimeoutStopSec` 被 SIGKILL，`stopped()` 的最终计数落盘也不会执行。
- 修复：`send` 加有界等待，超时即 `cancel()` 当前流（让持锁者返回、走重连退避）。见第三节 C。

### C3. 双方未配置 gRPC 消息上限：单节点约 1.8 万（两条入站）～3 万（一条入站）用户时 Snapshot 永远发不下去，节点静默脱管并无限重连 [读码]

- Agent `agent.go:361-371` `grpc.NewClient(...)` 没有 `grpc.WithDefaultCallOptions(grpc.MaxCallRecvMsgSize(...))` → grpc-go 默认接收上限 4 MiB。
- 面板 `grpc.rs:2338` `Server::builder().add_service(AgentChannelServer::new(..))` 没有 `max_decoding/encoding_message_size` → tonic 默认解码 4 MiB。
- 估算：VLESS Vision 一条凭据 `InboundUser` ≈ 96 B，`UserOp`（两条入站）≈ 238 B → 4,194,304 / 238 ≈ **17.6k 用户**；一条入站 ≈ 140 B → ≈ 30k。PERF.md 的目标是 1 万/节点，离悬崖只有 1.8 倍。
- 失败形态最糟：agent `stream.Recv` 得到 `ResourceExhausted: received message larger than max`，`done <- err` → 流结束 → 退避重连 → Hello → 面板再发同一个 Snapshot → 循环。面板记成 `no_ack` 失败并退避到 10 min，日志只有 "channel closed"。期间**撤销用户的变更永远到不了节点**。
- 修复：两侧显式设 64 MiB（agent `MaxCallRecvMsgSize(64<<20)`；面板 `.max_decoding_message_size(64<<20).max_encoding_message_size(64<<20)`），面板在 `sync_if_stale` 编码后记录 `snapshot_bytes` 指标并在 > 50% 上限时 WARN；M7 前把 Snapshot 分页（`ConfigSnapshot` + 后续 `UserDelta` 链）。

### C4. 面板：gRPC TLS 接入对"握手中"的连接无并发上限，公网端口可被低成本耗尽内存 [读码]

- `tlsserver.rs:125-145`：每个 accept 到的 TCP 都 `tokio::spawn` 一个握手任务，10 s 超时（`:38`）。`BACKLOG=128`（`:40`）只限制**已完成**握手的排队数，不限制进行中的。
- 每个握手任务持有 TcpStream + rustls `ServerConnection`（约 30–60 KiB 缓冲）最多 10 s。2 万 conn/s 的空连接 → 20 万任务 × ~40 KiB ≈ 8 GB。gRPC 端口必须对公网开放（agent 从任意地址出站拨入），前面没有反代。
- 带伪造客户端证书链的 ClientHello 还各自消耗一次链验证（ECDSA/RSA）。
- 修复：spawn 前 `Semaphore::try_acquire_owned`（如 1024），拿不到就直接丢弃 TCP；见第三节 D。

### 已核查、确认无问题的安全项（供对照）

- 面板↔agent 鉴权：身份只来自 mTLS 客户端证书序列号（`enroll::peer_cert`），`revoked_certs` 墓碑**先于**节点表查询（`node_for_serial_from`），续期证书"首次见到即吊销旧证"，重注册吊销全部旧序列号。不需要 timestamp/nonce：TLS 1.3 通道已绑定身份；`TrafficReport` 跨流重放对幂等高水位结算无害。
- 注册 token：256 bit、只存 SHA-256、`subtle::ct_eq`、所有失败同一 `PERMISSION_DENIED`、单次使用在节点行锁下条件 UPDATE 烧毁、按 IP 与全局限流。
- CSR：仅 P-256 / ecdsa-with-SHA256 / 无属性 / 长度上限 / 两次签名验证（x509-parser + rcgen）；证书字段全部由面板决定。
- 横向影响：一个被攻陷的节点只能看到自己的 desired state、只能给**自己已分配**的用户记流量（`node_users` / `node_users_departed` 准入），且受每键/每节点速率上限（`FLUSH_SQL`）、`MAX_REPORT_ROWS`、`MAX_DIRTY_SESSIONS_PER_NODE`、心跳字符串净化（`nodestat::agent_text`）约束。拿不到 CA 私钥，伪造不了别的节点。
- RCE/命令注入：agent 仅在特权更新器里 `exec.Command("systemctl", ...)`，参数全是常量或 root 控制的 flag；`-print-units` 对已校验副本执行、空环境、输出有界、30 s 超时；ACME 挑战 HTTP 服务只回答精确路径、有读写超时与头大小限制。xray 配置通过 `DecodeJSONConfig → Build` 强类型化，`refuseFakeDNS` 二次审查。
- Panic：面板非测试代码的 `unwrap`/`expect` 仅为 `Mutex::lock().unwrap()`（毒化只杀当前会话任务）与启动期 `install_default().expect`；agent 所有 `m.instance` 访问前都有 nil 检查。
- Goroutine 泄漏：`session()` 的 writer/reader/heartbeat/traffic 四个 goroutine 都由 `wg` 收口且 `defer cancel()` 先于 `wg.Wait()`；`renewLoop`/`leaseLoop`/`prober`/`certs.run` 都以进程 ctx 为界；`sendPendingReportLocked` 的匿名 goroutine 有 2 s 上限。未发现未受控退出的协程。
- 背压：面板 `read_permits=8` 限制并发 desired-state 读、`fetch_permits` 限制下载、`SEND_TIMEOUT=30s` 踢掉不读流的 agent、`WAKE_ALL_JITTER` 与随机 reconcile 相位；agent 的 `maxFinals=64`。

## 二、[臃肿与性能损耗]（Warning / Optimization）

### W1. Agent：每 10 s 全量重发 1 万行**未变化**的计数，并在 `CoreManager.mu` 内做 3.4 万次堆分配 [已测]

- `core.go:687-720` `countersLocked`：每用户两次 `"user>>>"+email+">>>traffic>>>uplink"` 拼接（2 次堆分配）→ 用刚拼出的字符串查 `m.mono` map → 为每个名字分配 `monoCounter`（`:77`，其注释自承"offset 在实践中始终为 0"，是 YAGNI 守卫）→ 把所有 email 收进切片并 `sort.Strings`（`:700`，面板按 user_id 索引，不需要顺序）。
- `monitor.go:78` 每 tick 发送全部 `counted` 用户，不管是否变化。200 节点 × 1 万用户 = **每 10 s 20 万行** 进面板，典型时段 >90% 是空操作，但面板 `traffic.rs::update_at` 对每行仍要做 UUID 解析、成员集查找、两次 DashMap 分片锁、两次 String 克隆（W3）。
- 本机基准（`BenchmarkTrafficSnapshot10k`）：**7.37 ms / 2.97 MB / 34,046 allocs 每 tick**，全部在 `mu` 之下（期间 `ApplyUserOps`、`Rebuild`、`handleDown` 全部等待）。
- 修复见第三节 A（已在副本上实现并全套 `-race` 测试通过）。

### W2. Agent：state hash 每次 Ack/Hello 做 4 万次 `[]byte(s)` 拷贝 [已测]

- `statehash.go:36-47` `field` 闭包对每个字段 `h.Write([]byte(s))`；user_id（36 B）与 account_json（~70 B）超过编译器栈分配阈值，每条记录 2 次堆分配，2 万条记录 = 4 万次。`sendAckLocked` 每次 delta 都调一次。
- 本机：**22.2 ms / 9.9 MB / 40,030 allocs**。换成复用的 scratch buffer 后 18.2 ms / 7.7 MB / **32 allocs**（剩余是 `recs` 与 `sorted` 两份 1.3 MB 的拷贝，可再省一半：直接对 `recs` 原地排序）。

### W3. 面板：`TrafficBuffer::update_at` 热路径每行两次 `String` 克隆 [读码]

- `traffic.rs:304` `(node_id, user_id, session.clone())` 作查找键（即使 entry 已存在也克隆）；`:336` `idx.sessions.entry(session.clone())` 再克隆一次。按 W1 的 2 万行/s 计，仅键就 **4 万次堆分配/s**。
- 根因是 `type Key = (Uuid, Uuid, String)`（`:75`）。agent 的 session id 永远是 `uuid.NewString()`（`monitor.go:16`，proto 注释也这么说）：把 `Key` 改成 `(Uuid, Uuid, Uuid)`（48 B、`Copy`、零堆），`update_at` 入口 `Uuid::parse_str` 失败即丢弃（现有 `valid_session_id` 已经只放行 ≤128 B 无 NUL 的串）；DB 列保持 TEXT，flush 时 `to_string`。保守方案：`Arc<str>`（引用计数替代分配）。

### W4. 面板：一次 desired-state 读构造 2–3 份用户集合副本，delta 路径对 want 做两遍 SHA-256 [读码 + PERF.md 数据]

- `grpc.rs:2028 desired_state` 从 DB 建 `Vec<UserOp>`（副本 1）；`:2189` `NodeState::of_snapshot(snap.inbounds_json.clone(), &snap.users)` → `user_set`（`:225`）把每个 user_id/tag/protocol/account_json **再克隆一遍**进 BTreeMap（副本 2，自家注释：~1.3 KB/用户 → 1 万用户 13 MB，8 个 permit 同时在飞 ≈ 100 MB 峰值）；`SetDigest::of`（`:449`）对每用户算 `user_digest`；随后 `diff_from_digest`（`:481`）对 want 的每个用户**重新**算一遍 `user_digest`，并 `add_op` 第三次克隆变更用户的字符串。
- PERF.md：`user_set` 3.34 ms、`state_hash` 1.12 ms（每次 1 万用户读）。变更→agent 的 2 s 目标里这是面板侧的主要 CPU。
- 修复：(a) `diff_from_digest(base, want_digest, want)` 复用已算好的 `want.users` 摘要（−1 万次 SHA-256/delta）；(b) `UserSet` 改为借用 `&snap.users` 的 `BTreeMap<&str, BTreeMap<&str, (&str, &str)>>`（`snap` 活到发送前，生命周期足够）→ 副本 2 消失。

### W5. 面板：`has_shadowsocks` 每次读都把整段 inbounds JSON 小写复制一份，再**深拷贝**整棵解析树 [读码]

- `grpc.rs:504-515`：`inbounds.to_ascii_lowercase()`（分配 = JSON 大小）→ `serde_json::from_str::<Value>` → `.as_array().cloned()`（克隆整个数组及其所有对象）→ 只为 `iter().any(...)`。被 `SetDigest::of` 调用，即每个会话每次 `decide`（≥ 200 次/分钟）。
- 而 `desired_state` 手里本来就有解析好的 `node.xray_inbounds: Value`，先 `to_string` 再在这里重新解析。
- 修复见第三节 E（3 行）。更好：在 `desired_state` 里从 `Value` 算一次 `shrink_unsafe` 随 `Desired` 带出。

### W6. Agent：重连与注册退避没有抖动 → 面板重启后全部节点同步重连（惊群） [读码]

- `agent.go:262 nextBackoff` 与 `enroll.go:106`：严格 1 s→2 s→4 s…→30 s。面板一次重启，200 个节点在同一个 100 ms 内做 TLS 握手、`node_for_serial_from` 查询、`record_agent_addr` UPDATE、`refresh_members`、desired-state 读（8 permit 排队）。面板 W14 为 reconcile 加随机相位正是因为这个 lockstep，但重连本身仍然同步。
- 修复：`d := time.Duration(float64(backoff) * (0.5 + rand.Float64()))`（full jitter），两处各 1 行。

### W7. Agent：`gateDispatcher` 一把全局 `sync.Mutex` 兼管 allowed/live/limits；心跳在锁内 O(keys) 扫描 [读码]

- `gate.go:58`。每个 dispatch（每条连接、每个 mux 子流）取锁两次（`admit`/`release`，`:197`）——临界区短，基准可接受；但 `LiveTotal`/`LiveStats`（`:156-178`）每 15 s 在同一把锁内遍历全部 live key 并建 map，`SetLimit` 也遍历全部 key。
- 修复：维护 `liveConns atomic.Int64` 与 `liveUsers atomic.Int64`（key 0→1 / 1→0 时增减），心跳读取 O(1) 无锁。流量计数本身用的是 xray 的 `stats.Counter`（atomic），无锁竞争，这点没问题。

### W8. Agent：`applyOpLocked` 对实例**每个** inbound 做 `Revoke + GetHandler + RemoveUser`，即使用户从未在该 inbound 上 [已测总量]

- `core.go:505-520`。全新 Rebuild 时 `cur` 为空，1 万用户 × 2 入站 = 4 万次空操作 `GetHandler`（各取一次 inbound manager 的 RWMutex）与 `RemoveUser`。本机 `BenchmarkRebuild10k` = 221 ms / 71 MB / 777k allocs（主要是 xray 自己的）。
- 注释说明这是防御（"过期凭据绝不能留活"），对 delta 保留它；Rebuild 路径上 `cur` 必为空，可直接跳过第一段循环。

### W9. 面板：热路径上的串行 I/O 与小 clone

- `grpc.rs:1949-1966 store_heartbeat`：每个心跳在流读取循环里**串行** await 两次 Valkey（`set_with_ttl`、`set_online`），期间该 agent 的下一条消息（可能是 TrafficReport）排队。合并成一次 pipeline，或 `tokio::spawn`。
- `grpc.rs` 中 54 处 `.clone()` 多数是 `Arc`/`Uuid`/`AppState` 的廉价克隆，真正的字符串复制集中在 W4。`api.rs` 63 处同类。
- 限流一致性：`enroll.rs::within` 与 `sub.rs::within_limit` 在 Valkey 故障时**失败开放**（注释有说明），`login_limit::Attempt::reserve` 失败关闭（500）。对 Enroll 来说开放意味着 Valkey 故障期间 CSR 验签 + DB 查询无上限；建议统一为"开放但本地令牌桶兜底"。
- `sess.sync.lock().unwrap()` 与 `lock_or_recover(&sess.agent)` 并存：同一文件两种毒化策略，统一用后者。

### W10. 架构与依赖：无过度设计，但有两个"体量"问题

- 没有 Java 式分层：handler 直接写 SQL，`enforce::SERVED` 等以常量拼接（全部 `AssertSqlSafe(format!)` 只拼常量，无用户输入），这是合理的。真正的问题是 `api.rs` 5,934 行 / 72 个 handler 一个文件，应按 nodes/users/auth 拆模块——组织问题，不是性能问题。
- `SyncState`（`grpc.rs`）15 个字段、`decide()` 9 个早退分支：复杂但由协议需求驱动，且有 30+ 个针对性单测覆盖，不建议动。
- 面板 406 个 crate：`chrono` + `time` 并存是 rcgen 的 API 强迫的；`hex` + `base64` + `data-encoding` 三个编码库可收敛为 `data-encoding` 一个（−2 crate，意义不大）；`mimalloc` 有 PERF.md 的实测依据。没有"为极小功能引入臃肿 crate"的情况。
- Agent 依赖干净：体积由 xray-core 决定（gvisor/wireguard/quic 随之而来）；`pebble`、`miekg/dns` 仅测试引用；`BurntSushi/toml` 解析 4 个键略重但可忽略。无接口抽象滥用：`userManager`/`proxyExposer` 是对 xray 内部类型的必要断言。

## 三、[重构前后代码对比]（Before vs After）

### A. Agent `core.go`：流量上报——预解析计数器 + 只发变化行（已在副本实现，`go test -race` 全绿）

**Before**（`core.go:77-82, 120, 687-740`）

```go
type monoCounter struct{ lastRaw, offset int64 }

type CoreManager struct {
    // ...
    counted map[string]struct{}
    mono    map[string]*monoCounter
}

func (m *CoreManager) countersLocked(only map[string]struct{}) []*pb.UserTraffic {
    sm, ok := m.instance.GetFeature(stats.ManagerType()).(stats.Manager)
    if !ok { return nil }
    set := only
    if set == nil { set = m.counted }
    emails := make([]string, 0, len(set))
    for e := range set { emails = append(emails, e) }
    sort.Strings(emails)                                   // 面板不需要顺序
    var out []*pb.UserTraffic
    for _, email := range emails {
        up := m.readCounter(sm, "user>>>"+email+">>>traffic>>>uplink")     // 每 tick 拼 2 万个字符串
        down := m.readCounter(sm, "user>>>"+email+">>>traffic>>>downlink")
        if up == 0 && down == 0 { continue }
        out = append(out, &pb.UserTraffic{UserId: email, UpBytes: uint64(up), DownBytes: uint64(down)})
    }
    return out
}

func (m *CoreManager) readCounter(sm stats.Manager, name string) int64 {
    raw := counterValue(sm, name)                          // 按名字查 map
    st := m.mono[name]                                     // 再按名字查 map
    if st == nil { st = &monoCounter{}; m.mono[name] = st } // 自承"offset 始终为 0"
    if raw < st.lastRaw { st.offset += st.lastRaw }
    st.lastRaw = raw
    return raw + st.offset
}
```

**After**

```go
// userCounters: 用户的 xray 计数器，装用户时解析一次（registerCountersLocked 在
// 用户能连上来之前就已注册；xray 从不注销），以及本流上最近一次报过的值。
type userCounters struct {
    up, down         stats.Counter
    sentUp, sentDown int64
}

func (m *CoreManager) registerCountersLocked(uid string) {
    if _, ok := m.counted[uid]; ok || m.instance == nil { return }
    sm, ok := m.instance.GetFeature(stats.ManagerType()).(stats.Manager)
    if !ok { return }
    up, err1 := stats.GetOrRegisterCounter(sm, "user>>>"+uid+">>>traffic>>>uplink")
    down, err2 := stats.GetOrRegisterCounter(sm, "user>>>"+uid+">>>traffic>>>downlink")
    if err1 != nil || err2 != nil { return }
    m.counted[uid] = &userCounters{up: up, down: down}
}

// all=false：只带上一次上报后发生变化的用户（周期上报）。全量（all=true）用于
// 最终计数、新流的第一次上报（ResetSent）与被移除用户的尾账。
func (m *CoreManager) countersLocked(only map[string]struct{}, all bool) []*pb.UserTraffic {
    var out []*pb.UserTraffic
    for uid, c := range m.counted {
        if only != nil {
            if _, ok := only[uid]; !ok { continue }
        }
        up, down := c.up.Value(), c.down.Value()           // 两次 atomic load，零分配
        if up == 0 && down == 0 { continue }
        if !all && up == c.sentUp && down == c.sentDown { continue }
        c.sentUp, c.sentDown = up, down
        out = append(out, &pb.UserTraffic{UserId: uid, UpBytes: uint64(up), DownBytes: uint64(down)})
    }
    return out
}
```
