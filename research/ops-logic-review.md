- 日期：2026-10-06
- 范围：akari-panel `origin/main` @ `235ce59`（W28-a #77 之后）。只读审查，没有改动代码。
- 方法：从运营者和付费用户的角度，把下单、支付、续费、换套餐、退款、佣金、提现、到期、流量、封禁、删除、通知这些业务流程走一遍。每一条结论都对照了代码（文件:行号）。没能完全核实的地方单独标注。

## 1. 结论摘要

- **共 21 项**：高 3、中 9、低 9。
- **最紧急的是换套餐折算（高-1、高-2）**：用户可以无限刷流量，也可以把优惠券、赠送套餐变现。代码没有错，但规则在运营上可以被利用，属于直接的收入损失。
- **重置订阅链接不能止损（高-3）**：用户点了"重置订阅"后，泄露或共享出去、已经导入客户端的节点凭据仍然有效。xboard 等同类面板的"重置订阅"会同时更换 UUID。
- **中等问题主要有三类**：
  - "管理员以为做了、其实没做"：后台退款时退款金额登记为 0；下架套餐会连带挡住老用户续费；删除用户不提示余额和提现。
  - "用户付了钱却没有得到预期结果"：流量用完后续费不恢复流量；售罄后付了款不开通。
  - "默认配置下用户收不到通知"：默认不验证邮箱，到期、流量和收据邮件全部不发。
- **计划覆盖情况**：PLAN-v0.4 和 SPRINT 队列**基本没有覆盖**这些问题。只有账号删除（W27 ⑤ 自助注销 / D10）、D5 节点额度、D9 倍率展示和设备限制（战略决策 3）在计划内。建议在 P1 之后增加两个 T1 批次（资金规则、套餐生命周期），见第 5 节。

## 2. 问题清单（按严重度）

### 高-1　换套餐会清零已用流量，但折算只按剩余时间算：来回切换就能无限刷流量

- **位置**：
  - `src/billing/catalog.rs:481` `switch_credit`：折算 = 标价 × 剩余时间 / 名义天数，不考虑已用流量。
  - `src/plans.rs:1363` `apply_set_user_plan` 调用 `sync_users_from_plan(..., true)`（`plans.rs:~1145`，`traffic_used_bytes = 0`）。
  - `allow_switch_in` 默认是 `true`（`1000_baseline.sql:696`）。
- **场景**：
  1. 站点有两个套餐：A（¥30/月，100 GB）和 B（¥30/月，100 GB），也可以是基础版和专业版。
  2. 用户第 1 天用完 A 的 100 GB，然后换到 B。折算约 ¥29，实付约 ¥1，B 从现在起算满一个月，流量清零。
  3. 第 2 天再换回 A。这次以 B 订单的**标价** ¥30 为基础折算，实付接近 0，流量再次清零。
  4. 如此循环，每天花几毛钱就能拿到一份满额流量。
  - 如果两个套餐价格不同，就是在高低档之间来回切换：升级只付差价，降级时多余的折算作废，每两次切换就得到两份满额流量。
- **运营为什么反对**：流量是成本最高的资源，这个规则直接打穿了流量配额。
- **建议**（给运营者一个开关）：
  1. 折算改为 `标价 × min(剩余时间比例, 剩余流量比例)`（只对有流量额度的套餐生效）。这和 v2board"按剩余价值折算"的思路一致。
  2. 或者换套餐时**不清零**已用流量：新套餐额度减去已用量，最低为 0。开关可选"清零 / 继承已用量"，默认继承。
  3. 可选的换套餐冷却期，例如 N 天内最多换 1 次，默认关闭。
  - 第 1 条或第 2 条至少要做一条。
- **是否在计划内**：否。

### 高-2　折算按"标价"计算：优惠券折扣、管理员赠送、已退款的订单都会变成可用的折算

- **位置**：
  - `src/billing/catalog.rs:481-510`：`paid` CTE 取 `o.list_price_cents`，过滤条件只有 `status='paid' AND fulfilled_at IS NOT NULL`。没有排除 `refunded_at`、`gift_cents`、`discount_cents`。
  - `src/billing/manual.rs:104`：赠送订单的 `list_price_cents` 是全价，`gift_cents` 也等于全价。
  - `docs/PAYMENTS.md` 写的"value = what was paid + any credit"与代码不符：标价里还包含了折扣和赠送部分。
- **场景**：
  - 优惠券：用户用一张 50% 券（只限套餐 A）买 A，标价 ¥100、实付 ¥50。随后立刻换到 B（¥100），折算约 ¥100，B 等于免费。券的 `plan_ids` 范围限制被绕过，¥50 的券变成了 ¥100 的价值。
  - 赠送：管理员手工赠送 A（标价 ¥100）。用户换到任意 ¥100 的套餐，不用付钱。"送 A"就变成了"送 ¥100 余额"。
  - 退款：一笔续费订单被退款后，它仍然算作"已付订单"，还能作为折算基数（与 P1 相关，见第 3 节）。
- **建议**：折算价值改用**实付价值** `list − discount − gift`，并排除 `refunded_at IS NOT NULL` 的订单；封顶值同样按实付合计。同步修正 PAYMENTS.md。
- **是否在计划内**：否。建议并入 P1 或紧跟 P1。

### 高-3　"重置订阅链接"只换链接，不换节点凭据：泄露或共享无法止损

- **位置**：
  - `src/sub/mod.rs:305` `rotate_token` 只更新 `users.sub_token_hash/enc`。
  - `src/entitle.rs:12-19`：设计上就是"已有账号在套餐或入站变动时保持不变"。
  - 全站没有"重置节点凭据"的接口（已检查全部 `/api/v1` 路由）。
- **场景**：
  1. 用户把订阅分享给朋友，或者链接泄露。
  2. 用户或客服点击"重置订阅"，旧链接失效。
  3. 已经导入客户端的 UUID / 密码继续可用，并继续消耗该用户的流量。
  - 唯一的止损办法是封禁用户，或者取消再重新分配套餐，而这样会清零流量和时间。
- **运营为什么反对**：这是客服最常处理的工单（"流量被偷用"）。用户以为已经处理好了，实际上没有效果。在设备限制推迟的前提下（决策 3），这是唯一的止损手段。
- **建议**：
  - 重置订阅时**同时重新生成**该用户在所有入口上的凭据，并 bump 相关节点，让 agent 断开旧凭据的连接。前台和后台的"重置订阅"按钮都改成这个行为，确认框写明"所有已导入的客户端需要重新导入"。
  - 也可以拆成两个按钮："仅换链接"和"换链接 + 凭据"，默认用后者。
  - 预计不需要改 proto，走现有的 user op 即可。**未核实** agent 侧在凭据替换时是否会断开旧连接，需要在 smoke 里验证。
- **是否在计划内**：否。

### 中-1　流量用完后"续费"不恢复流量，仍然照收全价

- **位置**：
  - `src/billing/catalog.rs:405` `decide`：同一套餐、非重置包、有到期时间，一律判为 `Renew`，不检查是否已用完。
  - `src/plans.rs:1491` `apply_renew_user_plan` 只延长到期时间（`sync_users_from_plan(.., false)`，不清零）。
  - PAYMENTS.md 写明"a renewal of a none-period plan extends the time, not the quota"。
- **场景**：
  1. 套餐为"30 天 100 GB，不重置"。用户第 20 天用完流量，被按额度停用。
  2. 商店仍然提供"续费"，用户付了全价，到期时间加 30 天，但仍然停用。
  3. 如果管理员没有给流量重置包定价，用户在到期前只能换别的套餐，或者等到期。
  - 月度重置的套餐在月中用完也一样：续费买不回流量。
- **建议**：
  - 服务端对"已按额度停用 + 不重置套餐"的续费，要么拒绝并引导购买重置包，要么提供开关"续费同时重置流量"（对一次性额度的套餐默认开启）。
  - 后台在"不重置套餐没有重置包价格"时给出警告。
  - 现在的 SPA 会优先选中重置包（`purchase.tsx:63-77`），但服务端不拦截。W36-b 换门户后，这个前端保护可能会丢失。
- **是否在计划内**：否。

### 中-2　售罄后付款"已付款未开通"：用户被扣款、收到"支付成功"邮件，管理员没有主动告警

- **位置**：
  - `src/billing/orders.rs:481-495`：开通时才检查容量，待支付订单不占名额。
  - `src/mail/notices.rs:224-262`：收据不检查 `fulfilled_at`，显示的到期时间取的是**当前有效**套餐（可能是旧套餐）。
  - `src/tickets.rs:1103` badges 不含未开通订单，只有仪表盘计数（`dashboard.rs:156`）。
- **场景**：
  1. 剩最后 1 个名额，两人同时扫码付款。后付的一方被扣款，但套餐没有开通。
  2. 后付的用户收到"支付成功，套餐到期：<旧到期时间>"的邮件。
  3. 管理员只有主动打开仪表盘才会发现。
  - 同一条路径也覆盖"付款时套餐被停用 / 删除"和"余额不足"。
- **建议**：
  - 下单时为容量做预留（和优惠券一样：释放 / 兑现）。
  - 或者开通失败时自动退到余额，并通知用户（开关："开通失败自动退余额"）。
  - 收据邮件区分"已开通 / 处理中"。
  - 未开通订单接入管理员告警（Telegram / 邮件）和后台角标。
- **是否在计划内**：否。

### 中-3　在支付宝后台退款后，退款金额登记为 0，仪表盘和导出漏记退款

- **位置**：`src/billing/orders.rs:381` `cash_part = if to_balance { amount } else { 0 }` → `refund_cents = credit`；`src/dashboard.rs:139-141` 和导出 `export.rs:424` 用的都是 `refund_cents`。
- **场景**：
  1. 管理员在支付宝商家后台原路退款 ¥100，再到面板登记退款（不勾选"退到余额"）。
  2. 订单的 `refund_cents = 0`，仪表盘的"退款"不增加，营收虚高 ¥100。
  3. 对账时无法从面板看出这笔钱已经退回。
- **建议**：分开记录 `refund_to_balance_cents` 和 `refund_external_cents`（外部原路退款金额），仪表盘和 CSV 两者都显示。以后面板直接调用 `alipay.trade.refund`（SPRINT 已列为可选待办）时，自动填写外部退款金额。
- **是否在计划内**：部分在计划内。"面板内调用退款接口"是低优先级可选待办，但登记口径的问题没有被提到。

### 中-4　佣金过了冻结期就无法追回；默认冻结 7 天，远短于退款窗口

- **位置**：
  - `src/billing/commission.rs:276` `reverse_for_order` 只撤销 `pending` 状态的佣金。
  - 余额账本不允许出现负数（PAYMENTS.md "Balance"）。
  - 默认 `hold_days = 7`（`1000_baseline.sql:1006`）。
- **场景**：
  1. 被邀请人付款 ¥300，邀请人获得 ¥30 佣金，7 天后入账。
  2. 邀请人立即申请提现，管理员批准。
  3. 第 10 天被邀请人要求退款，退款完成，但 ¥30 佣金追不回。
  - 用小号互相邀请、付款、退款的套利更容易（另见低-7）。
- **建议**：
  - 退款时，对已入账的佣金写一笔"佣金追回"的负向账本。余额不足时记为欠款，后续佣金优先抵扣，并冻结提现。
  - 或者把"可提现"限制为入账超过 N 天、且订单未退款的佣金。
  - 退款对话框显示"该订单佣金已入账 ¥x，是否追回"。
- **是否在计划内**：否。

### 中-5　修改套餐（降额度、移除节点组、降速）会立即作用于所有已付费用户，没有预览、通知或保留老用户的选项

- **位置**：`src/plans.rs:828` `apply_update_plan` 对所有 `active` 持有者立即 reconcile、sync、bump。额度下降后，下一次流量检查（`enforce.rs:85`）就会停用超额用户。
- **场景**：管理员把"年付 1 TB/月"改成 500 GB/月。已经用了 600 GB 的年付老用户立刻被停用。用户没有收到任何解释，只有超额邮件（而且前提是邮箱已验证）。
- **运营为什么反对**：已经预付的用户权益被单方面改变，容易引发投诉和退款纠纷。管理员很可能只想"以后新卖的按新规格"。
- **建议**：
  - 保存前显示影响预览：受影响人数，会被立即停用的人数，失去的节点。
  - 二次确认，可选"邮件通知受影响用户"。
  - 长期方案：提供开关"仅对新购 / 续费生效"，即把套餐规格快照到 `user_plans`。这个改动较大，可以只做前两项。
- **是否在计划内**：否。W33-b 重写后台时可以加预览，但卡片里没有提到。

### 中-6　"下架"或"停用"套餐会挡住现有用户续费和购买重置包

- **位置**：
  - `src/billing/api.rs:296` `SALE_PLAN_SQL ... WHERE p.enabled AND p.on_sale`。
  - 下单时 `api.rs:613` 也用这个条件，不满足就返回 `NotForSale`。
  - 后台文案是"上架（在购买页出售）"（`spa/src/pages/admin-plans.tsx:595`），没有提到会影响续费。
- **场景**：管理员想停止对新用户销售某个老套餐，取消了"上架"。所有持有该套餐的用户都无法续费，到期后被迫换套餐（流量清零，价格可能更高）。正确的做法是"仅限续费"，但界面没有引导。
- **建议**：
  - 下架时提示"N 名现有用户将无法续费；只想停止新购请改用'仅续费'"。
  - 或者改变语义：`on_sale=false` 只对非持有者隐藏，`enabled=false` 才是彻底停售。
- **是否在计划内**：否（W33-b 可以顺带处理）。

### 中-7　管理员删除用户不检查余额、待审提现、待支付订单和有效套餐，也没有影响摘要

- **位置**：`src/api.rs:1373` `apply_delete_user` 直接执行 `DELETE FROM users`。
- **场景**：
  - 用户有 ¥200 余额（其中 ¥150 是可提现佣金），被直接删除，钱随账号消失。
  - 待审提现的资金已经扣除，只能批准（PAYMENTS.md）。
  - 待支付订单在删除后才到账，结果是"已付款未开通"，而且无法退到余额（`order_admin.refund_user_gone`）。
- **建议**：删除前返回影响摘要（余额、可提现金额、待审提现、待支付订单、套餐剩余天数），二次确认时列出这些数字。有待支付订单时先关闭订单。规则与即将实现的自助注销 / D10 统一：有余额或待审提现时，默认拒绝自助注销。
- **是否在计划内**：部分在计划内。W27 ⑤ 自助注销和 D10 有"二次确认"，但没有写余额和提现规则。建议在 ⑤ 的验收标准里补上。

### 中-8　默认不验证邮箱，导致到期、流量和收据邮件全部不发

- **位置**：
  - `src/mail/notices.rs:36` `RECIPIENT` 要求 `email_verified_at IS NOT NULL`，收据（`notices.rs:235`）同样如此。
  - D1 规定"注册需要验证邮箱"默认关闭。
  - 未验证注册写入的 `email_verified_at` 为 NULL（`signup/register.rs` `apply_register_unverified`）。
- **场景**：按默认配置上线后，所有自行注册的用户都收不到"即将到期"和"流量 80%/100%"提醒，续费率下降。后台注册设置页有一条警告（`signup/mod.rs:157-160`），但通知设置页和仪表盘都看不出"有 N% 的用户收不到提醒"。
- **建议**：
  - 门户在显眼位置引导用户验证邮箱（例如首次购买后提示）。
  - 邮件设置页显示"已验证地址的用户占比"。
  - 可选开关"向未验证地址发送到期和流量提醒"（只发提醒类邮件，不发找回密码），默认开启。
  - 由运营决定。
- **是否在计划内**：否。W36-b 门户可以加入验证引导。

### 中-9　缺少关键的用户通知：封禁、退款、管理员改套餐 / 取消套餐、提现结果、佣金入账

- **位置**：邮件种类只有 `register_code/…/order_paid/expiry_soon/expired/quota_80/quota_100/ticket_*/node_alert/announcement/admin_notice`（`1000_baseline.sql:1537`）。
- **场景**：
  - 管理员取消套餐或退款（包括 P1 修复后的自动撤销），用户只会在连不上时才发现。
  - 提现被驳回时，用户没有任何通知。
  - 被封禁的用户只有登录门户才能看到原因。
- **建议**：增加 `plan_changed`（含取消、退款撤销）、`refund`、`withdrawal_decided`、`banned` 四类模板，都可以在后台开关，并复用现有的模板和 outbox。P1 修复时至少带上 `refund`。
- **是否在计划内**：否。

### 低-1　取消套餐后仍会收到"套餐即将到期 / 已到期"邮件

- **位置**：`src/plans.rs:1585` 取消后 `users.expires_at` 保持不变（注释："enforced limit and expiry stay as they were"）；`notices.rs:97-123` 按 `users.expires_at` 发送。
- **场景**：用户的套餐被取消或退款撤销后，原到期日前 N 天仍会收到"即将到期，请续费"，到期后再收到"已到期"。
- **建议**：提醒类邮件只发给有 `user_plans.status='active'` 的用户。或者取消时把 `users.expires_at` 设为 `now()`，这会影响"记录"的语义，需要评估。

### 低-2　退款不释放优惠券次数；已退款订单仍算"首单"或"已付订单"

- **位置**：`orders.rs:351` `apply_refund` 不调用 `coupons::release`；`commission.rs:177-180` 的首单判断和 `new_users_only` 都没有排除 `refunded_at`。
- **影响**：
  - 用户退款后无法再用同一张限次券。
  - 新人券或首单返利因为一笔已退款的订单失效，邀请人拿不到正常首单的佣金。
- **建议**：已退款订单不计入"已付订单"类判断；优惠券次数是否返还做成退款对话框的选项。

### 低-3　降级时多出的折算直接作废；从永久套餐换出时没有折算，也没有提示

- **位置**：`catalog.rs` 的 `forfeited_cents`，以及 `credit = 0 when no expiry`。
- **影响**：
  - 商店虽然显示了作废金额，但用户仍可能投诉。
  - 永久流量包用户换套餐时，剩余流量和永久权益全部丢失，界面只显示"折算 0"。
- **建议**：作废部分提供开关"转为余额（不可提现）"；从永久套餐换出时增加明确的确认提示。

### 低-4　迟到付款按"到账时"的状态履约，可能替换掉用户之后另购的套餐

- **位置**：`orders.rs:437` `grant` 按支付时的当前套餐重新判断续费 / 新购 / 换套餐。只有带折算的订单才标记 `credit_source_changed`。
- **场景**：
  1. 用户下单买 B，没有付款，订单过期，但支付宝关单失败。
  2. 用户改为续费 A 并付款成功。
  3. 之前 B 的二维码被支付，面板履约 B：替换 A，A 的流量清零，A 刚续的时间作废。
  - 前提是关单失败，概率较低。
- **建议**：订单记录下单时的动作；履约时如果动作发生了变化（续费变成换套餐，或者新购变成替换），转为"已付款待处理"或自动退到余额，不要静默替换。

### 低-5　没有部分退款

- **位置**：`orders.rs:351` 退款只能整单退。
- **影响**：常见的"按剩余天数退款"只能先整单退，再手工调整余额（负向调整受余额限制）。建议在 P1 的退款对话框里增加"退款金额"（不超过实付），套餐撤销按比例或可选是否撤销。

### 低-6　封禁不暂停到期计时；被封禁的邀请人仍按期获得佣金

- **位置**：`api.rs:1157` `apply_ban_user` 不影响 `user_plans`；`commission.rs:211` `credit_due` 不检查邀请人状态。
- **影响**：误封解除后用户损失了天数。因欺诈被封的邀请人仍然获得佣金入账，待审提现也不受影响。
- **建议**：提供开关"封禁期间暂停计时"（解封时把到期时间顺延封禁时长），默认关闭。邀请人被封禁期间的佣金保持待入账。

### 低-7　自邀返利只靠"无环"约束

- **位置**：`users_inviter_acyclic` 只禁止自己邀请自己和循环邀请。
- **影响**：用小号邀请大号，返利就等于永久折扣，并且可以提现。返利默认关闭、默认只返首单，所以列为低。
- **建议**：返利开启时，可选"同注册 IP 或同支付宝买家不返利"（支付宝通知里有 `buyer_id`，可以记录下来用于比对）。

### 低-8　没有可用支付方式时，余额或折算全额覆盖的订单也无法下单

- **位置**：`billing/api.rs:539` `create_order` 先检查 `any_usable()`；`shop` 的 `enabled` 同样依赖这一点。
- **影响**：支付宝维护或停用期间，有余额的用户也无法续费，商店为空。
- **建议**：只有需要支付渠道的订单（`amount > 0`）才要求有可用的支付方式。

### 低-9　商店展示"设备数"，但实际不限制

- **位置**：`billing/api.rs` 商店返回了 `device_seats`；PAYMENTS.md 写明"not enforced until the client ships"。
- **影响**：宣传与实际不一致。按决策 3 现在不做设备限制，但建议在门户隐藏这个字段，或标注"即将支持"。

## 3. 与 P1（退款撤销套餐）相关的缺口

P1 方案需要同时处理以下几点，否则修复后仍有漏洞：

1. **已退款订单仍参与换套餐折算**（高-2）：P1 回滚续费订单后，该订单仍是 `status='paid'`，还可以作为 `switch_credit` 的"latest"或计入封顶值。需要在 `switch_credit` 里加 `AND o.refunded_at IS NULL`。
2. **退款登记口径**（中-3）：P1 改造退款对话框时，顺便记录外部原路退款的金额。
3. **佣金追回**（中-4）：P1 的事务里已经调用了 `reverse_for_order`，建议同时处理已入账佣金的追回或冻结。
4. **退款通知**（中-9）：P1 会自动撤销用户的套餐，必须给用户发邮件，否则用户只会发现"连不上了"。
5. **取消后仍发到期提醒**（低-1）：P1 结束订阅后，`users.expires_at` 仍是未来时间，会继续发"即将到期"提醒。
6. **部分退款**（低-5）：P1 在设计"撤销预览"时，可以一并考虑退款金额与撤销天数的对应关系。
7. **优惠券次数和首单判断**（低-2）：退款后的处理。

## 5. 建议的修复批次

按队列"串行、单 PR"的规则排列。

1. **批次 A：资金规则（T1，并入 P1 或紧跟 P1）**
   - 高-2：折算按实付计算，排除已退款和赠送订单。
   - 中-3：退款金额分开登记。
   - 中-4：佣金追回或冻结。
   - 低-2：退款与首单、优惠券的判断。
   - 低-5：部分退款（可选）。
   - 退款通知邮件（中-9 的一部分）。
   - 测试：每条规则配一个金钱不变量测试；smoke 覆盖"优惠券 → 换套餐"和"赠送 → 换套餐"不再能套现。
2. **批次 B：套餐生命周期（T1）**
   - 高-1：换套餐时继承已用量，或折算扣除流量（带开关）。
   - 中-1：已用完流量时的续费处理。
   - 中-2：容量预留，开通失败自动退余额，收据区分状态，管理员告警。
   - 低-3：作废折算的处理和永久套餐换出提示。
   - 低-4：迟到付款不静默替换套餐。
   - 低-8：余额下单不依赖支付方式。
3. **批次 C：订阅凭据重置（T1，panel 加 smoke 验证 agent 断线）**
   - 高-3：重置订阅时同时更换所有入口的凭据，前台和后台的按钮与确认文案一起改。
4. **批次 D：运营体验与通知（T2，可以放进 W33-b / W36-b，或者单独一个 PR）**
   - 中-5：改套餐的影响预览和通知。
   - 中-6：下架的提示和语义。
   - 中-7：删除用户的影响摘要（与 W27 ⑤ 共用实现）。
   - 中-8：邮箱验证引导和已验证占比。
   - 中-9：其余通知模板（套餐变更、提现结果、封禁）。
   - 低-1：取消后的提醒。
   - 低-6：封禁时暂停计时、佣金暂缓（开关）。
   - 低-7：返利风控（可选）。
   - 低-9：设备数展示。

**排期建议**：A 和 C 风险最高，而且改动不大，建议排在队列 ②（服务器拆分）之前或紧随其后。B 需要先由用户拍板几个开关的默认值：换套餐时流量"继承"还是"折算扣除"，售罄时"预留"还是"自动退余额"。D 跟随后台和门户的重写一起做。
